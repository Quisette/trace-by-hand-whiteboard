# Jev's API, and this repo's Jev-compatible implementation

TypeSafe AI's **Jev** is a "System One" model: it does not write text, it answers typed questions about some content
in a single call. This document records what the real API looks like (so `src/jev.js` can speak it), where that
information came from, and what is still an assumption.

## The API

Base URL `https://api.typesafe.ai` *(confirmed, `TYPESAFE_BASE_URL` overrides)*. JSON in, JSON out.
`Authorization: Bearer <key>` *(confirmed; key from `TYPESAFE_API_KEY`)*. Responses carry `x-typesafe-request-id`.

### `POST /v1/systemone`

```jsonc
{
  "state": "I was charged twice. Please help.",     // text, an object or an array: the content every question is about
  "model": "jev-latest",                             // required; names come from GET /v1/models
  "questions": {                                     // at least one; the names are yours and key the answers
    "billing": {"type": "noul",   "instructions": "Is this about billing?",
                "criteria": {"true": "...", "false": "..."}},        // criteria optional; instructions optional if an outcome is described
    "tone":    {"type": "choice", "instructions": "What is the tone?",
                "criteria": {"calm": null, "angry": "An upset or hostile message"}},   // label -> description (text, object, array or null)
    "urgency": {"type": "score",  "instructions": "How urgent is this?",
                "criteria": ["Can wait", "Needs attention this week", "Needs attention today"]}  // ordered; position = score from 0
  }
}
```

Descriptions (`instructions` and every criterion) may be text, a JSON object or an array. A choice without a description
"is interpreted by its name alone". `extra_body` fields are merged over the body by the SDK (the server may ignore them).

Response `200`:

```jsonc
{
  "model": "jev-latest",                              // the model that answered; may differ from the requested alias
  "answers": {
    "billing": {"type": "noul",   "noul": 0.98},      // probability of yes. Nothing else: no confidence
    "tone":    {"type": "choice", "choice": "angry", "confidence": 0.9, "probabilities": {"calm": 0.1, "angry": 0.9}},
    "urgency": {"type": "score",  "score": 1.7, "confidence": 0.9,    // probability-weighted level, may fall between integers
                "legend": {"0": "Can wait", "1": "...", "2": "..."}, "probabilities": {"0": 0.1, "1": 0.1, "2": 0.8}}
  },
  "usage": {"input_tokens": 120, "output_tokens": 12}  // output tokens are currently free
}
```

Answer `type` always equals the question's `type`. Unknown future answer types should be ignored by clients (the SDK does).

### `GET /v1/models`

`{"models": [{"name": "jev-latest", "description": "...", "release_date": "2026-09-15"}]}`. Names include aliases.

### Errors

| Status | SDK class | Body *(confirmed shape for 422; others assumed)* |
|---|---|---|
| 400 / 401 / 403 / 404 | `BadRequest`, `Authentication`, `PermissionDenied`, `NotFound` | the SDK reads `detail`, `error` or `message` (string or `{message}`) |
| 422 | `UnprocessableEntity` | FastAPI/pydantic: `{"detail": [{"type", "loc": ["body", "questions", "tone", "choice", "criteria"], "msg", "input"?, "ctx"?}]}`; for a discriminated union the question's type is part of `loc` |
| 429 | `RateLimit` | honours `retry-after-ms` then `retry-after` (seconds or HTTP date) |
| 5xx | `InternalServerError` | — |

SDK defaults: 10 s timeout per request, 2 retries on 408 / 429 / 5xx and connection errors, backoff 0.5 s doubling to 5 s with 25 % jitter, 30 s total budget.

## What this repo implements

| File | What |
|---|---|
| `src/jev.js` | The API contract: `Jev.systemOne(body)` (request → response), `Jev.validate(body)` (pydantic-style error list), `Jev.handle({method, path, headers, body})` (the whole HTTP surface incl. auth, CORS, errors) |
| `tools/jev-server.js` | A zero-dependency Node server over `Jev.handle`: `node tools/jev-server.js [--port 8787] [--key SECRET]` |
| `src/jev-client.js` | `JevClient`, a fetch-based client with the SDK's behaviour (auth, retries with `Retry-After`, typed errors, `.nouls/.choices/.scores`); works in Node and browsers |
| `src/nlboard.js` | Asks Jev in this format; `NLBoard.prime(client)` re-asks a real/compatible API for the sentences the local engine answered |
| `tests/jev-api.js`, `tests/conformance.py`, `tests/sdk_e2e.py` | wire-format tests, validation against the official models, the official SDK against the server |

### How the local engine reads a question

It is an exemplar matcher, not a language model. Each criterion description becomes a set of example phrases (a string,
every string in an array, and every string inside an object, so the documented `{"meaning": …, "examples": […]}` form
works; a bare label counts as an example). The state's text and each example are turned into token, token-bigram and
character-trigram features; an example's score is how much of it appears in the state, blended with trigram overlap.

- **choice**: softmax over the label scores → `probabilities`; `confidence` blends distribution sharpness and the top-two margin.
- **score**: softmax over the levels → `probabilities`, `score` = Σ level × probability, `legend` echoes the criteria.
- **noul**: the yes examples against the no examples; a side that is not described uses a fixed baseline; with neither (instructions only) the answer is `0.5`, "unsure".
- `instructions` are **not** used: the hosted model reads them, this matcher cannot.
- `usage` is an estimate (about 4 characters per token); the models are `jev-latest` (alias) and `jev-local-1`.

The whiteboard asks four questions per sentence in one call (intent, component type, negation, pointer step), so the same
questions work against the hosted model unchanged. The local engine is deterministic and offline; the hosted one will
understand sentences the examples do not cover.

## Assumptions and differences

- **Error bodies other than 422** (`401`, `404`, `405`, `413`) use `{"detail": "..."}`. The SDK accepts several shapes; the real service's wording is unknown.
- **Unknown model → 404.** The SDK has `NotFound` but the service's choice is not documented in what was read.
- **Stricter than the wire schema:** a noul question with neither instructions nor a described outcome, and a choice question with no choices, get a 422 `value_error`. The wire model accepts both, the SDK rejects both client-side.
- **Unknown request fields are ignored** (pydantic's default); the SDK's own question classes forbid them client-side.
- **Rate limits, body size limits and billing** of the hosted service are not known; the local server only enforces a 1 MB body limit.
- The `Authorization` check is optional (`--key`); without it any bearer token is accepted.
- Browsers can only call the hosted API if its CORS policy allows it; `tools/jev-server.js` sends `access-control-allow-origin: *`.

## Using it

```bash
node tools/jev-server.js --port 8787                              # the local Jev-compatible API

# the official SDK, unchanged:
TYPESAFE_BASE_URL=http://127.0.0.1:8787 TYPESAFE_API_KEY=anything python -c "
from typesafe_sdk import TypeSafeClient, Choice
with TypeSafeClient() as c:
    print(c.system_one('I need a technical fix', {'t': Choice(criteria={'billing': None, 'technical': None})}).choices['t'])"

# the whiteboard asking an API (local first, the API's answers replace them as they arrive):
open public/index.html?jev=http://127.0.0.1:8787
```

Tests: `node tests/jev-api.js`. With `SDK_PYTHON=/path/to/python` (an interpreter with `typesafe-sdk` installed, e.g.
`uv venv v && VIRTUAL_ENV=v uv pip install typesafe-sdk`) it also validates every request, response and error against the
official generated models, compares the 422 error lists with pydantic's, and runs the official SDK against three servers
(open, key-protected, and one that answers 429 first).
